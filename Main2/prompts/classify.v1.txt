RULES
- The DESCRIPTION is the primary evidence. The SUMMARY (title), the selected service and the request type in <intake_metadata> may be wrong or misleading on purpose.
- Report separately which work type the SUMMARY implies (summary_implies) and which the DESCRIPTION implies (description_implies). work_type follows the description. title_mismatch = true when they differ or the text says the title is misleading.
- work_type: "Incident" = something is broken, degraded, rejected, delayed, failing, or a monitoring/vendor alert about a fault. "Service Request" = a standard ask: access, licence, provisioning, removal, information.
- service must be exactly one catalogue name or UNKNOWN. Choose the system where the problem or request actually sits. Ignore neighbouring systems that are only mentioned as context ("already matched", "rather than ...", "not a ... issue"). The selected service may be an intake guess: keep it only if the text supports it.
- Access, licence, permission and removal requests belong to the business application they are for, exactly as in the ticket history ("Access requested for Cash Management" -> Cash Management), even though the identity team grants the access. Choose Identity & Access Management only for identity-lifecycle work with no single target application: multi-factor / SSO / password problems, account lockouts, deactivating leavers or inactive accounts across systems.
- "Emailed Support Tickets" is a channel, not a system. If the ticket arrived by email and no underlying system can be identified, return UNKNOWN.
- unclear = true only when the description lacks the information needed to act. Do not flag ordinary tickets.
- confidence is your own 0..1 certainty about the service. Give one short reason per decision, quoting evidence from the ticket.
- <advisory_ranking> is a deterministic keyword ranking with evidence; use it as a hint, not as truth.
